# Дашборд воронки продаж (PHP) — описание для проверяющего

## Назначение и сценарии

Встроенное приложение Битрикс24 (левое меню / вкладка), работающее от
лица авторизованного пользователя портала. Реализовано:

- **Сводка по стадиям воронки** — количество и сумма сделок по каждой
  `stageId` (основная воронка), с человекочитаемыми названиями стадий.
- **KPI**: сумма открытых сделок, число выигранных сделок за выбранный
  период (по `stageSemanticId === 'S'`), средний чек по выигранным.
- **Последние сделки**: 15 последних (название, сумма, стадия,
  ответственный).
- **Фильтр по периоду** (`dateFrom` / `dateTo`, по дате создания),
  по умолчанию — последние 90 дней; некорректный ввод обрабатывается
  с понятным сообщением, без падения.

Каждый пользователь видит данные ровно в рамках своих прав на портале —
запросы к `/v1/deals` идут с его сессионным токеном
(`Authorization: Bearer`, из `X-Vibe-Authorization`), а не с ключом
владельца приложения.

## Запрошенные скоупы и обоснование

| Скоуп   | Зачем |
|---------|-------|
| `crm`   | Чтение сделок (`POST /v1/deals/search`) и справочника стадий (`GET /v1/statuses`) для сводки, KPI и списка последних сделок. Запись в CRM приложение не производит. |
| `users` | Чтение имени/фамилии ответственного (`POST /v1/users/search`) для таблицы последних сделок. |

Ключ типа **авторизации (`vibe_app_`)** — приложение встраивается в
портал и многопользовательское. Рекомендуется режим `READONLY`, если
платформа его поддерживает: запись в CRM не требуется. Отдельно нужен
собственный `X-Api-Key` этого приложения на сервере (см. README,
раздел «Архитектура») — без него любой вызов к сущностям отклоняется.

## Известные ограничения

- Учитывается только основная воронка (`categoryId = 0`); выбор
  направления продаж для порталов с несколькими воронками не
  реализован — осознанно вынесено за скобки MVP.
- Максимум 1000 сделок за период (защита от избыточной выгрузки);
  платформенный потолок одного поиска — 5000.
- Названия полей у `statuses`/`users` (`id`/`name`, `name`/`lastName`)
  приняты по общей camelCase-конвенции платформы, подтверждённой для
  сделок, но не проверены отдельной страницей документации для этих
  двух сущностей — см. README, «Единственное оставшееся допущение».
- Точка деплоя — `php -S 0.0.0.0:3000 -t public router.php`. Для
  серьёзной нагрузки лучше `nginx + php-fpm` с тем же роутингом.

## Инструкция для проверяющего

1. Открыть приложение из левого меню / вкладки CRM на тестовом портале.
2. Убедиться, что дашборд загружается для сделок текущего пользователя
   без ручного логина внутри портала (сессия берётся из Gateway).
3. Проверить фильтр периода: задать заведомо пустой диапазон — должно
   показаться сообщение «сделок не найдено», без ошибки на экране.
4. Проверить `GET /api/me` — фактический тип ключа и скоупы должны
   совпадать с таблицей выше.
5. Проверить, что при недостатке прав приложение показывает понятное
   сообщение, а не техническую трассировку PHP.
6. Убедиться, что в коде и в `public/*` нет секретов — `VIBE_APP_KEY`
   читается только из окружения сервера (`.env`, не коммитится).
