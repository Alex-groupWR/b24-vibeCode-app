# Дашборд воронки продаж (PHP) — Сопроводительное описание

## 1. Назначение приложения и реализованные сценарии

Приложение представляет собой встраиваемый аналитический модуль для Битрикс24 (интегрируется в левое меню или слайдер/вкладку CRM), спроектированный по архитектурному паттерну **Backend For Frontend (BFF)** на стеке PHP 8.3. Сервис работает строго от лица авторизованного пользователя корпоративного портала: каждый сотрудник видит аналитику исключительно в рамках назначенных ему прав в CRM. Проброс контекста осуществляется трансляцией сессионного токена пользователя из заголовка `X-Vibe-Authorization` в запросы к шлюзу платформы, что исключает возможность несанкционированной эскалации привилегий.

### Ключевые сценарии:
* **Сводка по этапам воронки:** автоматическая агрегация числа и общего объема сделок по каждому этапу (`stageId`) основной воронки с сопоставлением технических ID с читаемыми названиями стадий.
* **Расчет бизнес-KPI:** динамическое вычисление суммы открытых сделок, числа выигранных сделок за выбранный период (`stageSemanticId === 'S'`) и среднего чека по успешным сделкам.
* **Реестр последних сделок:** табличный вывод последних 15 сделок с указанием наименования, суммы, текущей стадии и ответственного сотрудника (с получением имени и фамилии через API пользователей).
* **Гибкая фильтрация по периоду:** выбор диапазона дат создания сделок (`dateFrom` / `dateTo`) со стандартным значением по умолчанию — последние 90 дней. Граничный и некорректный ввод обрабатывается штатно, без сбоев интерфейса и падений сервера.

## 2. Запрошенные скоупы и их обоснование

Архитектура приложения реализует принцип минимально необходимых привилегий (Least Privilege). Бэкенд выполняет исключительно чтение данных:

| Скоуп | Назначение и техническое обоснование |
| :--- | :--- |
| **`crm`** | Чтение реестра сделок (`POST /v1/deals/search`) и системного справочника стадий (`GET /v1/statuses`) для формирования сводок, расчета KPI и построения таблицы сделок. Любые операции модификации (создание, обновление, удаление) в CRM исключены. |
| **`users`** | Чтение учетных записей сотрудников (`POST /v1/users/search`) строго для разрешения ID ответственных лиц в человекочитаемые «Имя Фамилия» в таблице сделок. |

> **Политика безопасности:** Для взаимодействия приложения с платформой используется ключ авторизации приложения (`vibe_api_`) в режиме **READONLY**. Секретный ключ изолирован на сервере в переменных окружения (`vibe_api_`), недоступен клиентскому коду (`public/`) и исключен из системы контроля версий.

## 3. Известные ограничения (MVP)

* **Единая воронка:** аналитика строится строго по основной воронке (`categoryId = 0`); поддержка кастомных направлений продаж и туннелей вынесена за рамки текущего релиза.
* **Ограничение выборки:** действует защитный лимит выборки до 1000 сделок за запрашиваемый период для предотвращения деградации производительности рантайма и браузера (платформенный предел шлюза — 5000 записей).
* **Конвенция схемы полей:** поля вспомогательных справочников (`statuses`: `id`/`name`, `users`: `name`/`lastName`) завязаны на стандартную camelCase-схему платформы.
* **Серверный рантайм:** текущий контур развернут с использованием встроенного веб-сервера (`php -S 0.0.0.0:3000 -t public router.php`), оптимального для микросервисной среды Вайбкод. Под повышенную эксплуатационную нагрузку архитектура готова к миграции на связку Nginx + PHP-FPM.

## 4. Инструкция для проверяющего

1. **Запуск из Битрикс24:** откройте приложение через пункт главного левого меню или раздел установленных приложений на тестовом портале (`b24-ou8bzw.bitrix24.ru`).
2. **Проверка бесшовной сессии:** убедитесь, что приложение загружается без дополнительных запросов логина/пароля — контекст и права пользователя подтягиваются автоматически через Gateway.
3. **Проверка фильтра и валидации:**
    * Установите заведомо будущий диапазон дат (когда сделок заведомо нет) — интерфейс должен отобразить аккуратную заглушку «Сделок не найдено» без генерации сетевых ошибок 500 или разрушения верстки.
    * Сбросьте период на значение по умолчанию (90 дней) и проверьте пересчет метрик KPI.
4. **Контроль скоупов и контекста (`GET /api/me`):** в панели разработчика (DevTools -> Network) найдите запрос к `/api/me` и проверьте, что набор скоупов соответствует заявленным (`crm`, `users`).
5. **Обработка нештатных ситуаций:** убедитесь, что при прямом обращении к API без сессии возвращается корректный JSON с кодом ошибки без утечки системных трассировок PHP.
6. **Аудит безопасности репозитория:** проверьте репозиторий GitHub — убедитесь, что в публичном коде отсутствуют захардкоженные токены (`vibe_api_`, `vibe_app_`), а файл `.env` внесен в `.gitignore`.
