# Дашборд воронки продаж — Битрикс24 Вайбкод (PHP, v2 — под реальный API)

Эта версия построена по фактической документации платформы
(`vibecode.bitrix24.tech/docs`), а не по предположениям — см. правки
ниже. Реализует все пункты задания: сводка по стадиям, KPI, 15
последних сделок, фильтр по периоду создания.

## Что изменилось по сравнению с первой версией

Первая версия (без доступа к реальной документации) угадывала имена
методов по аналогии со стандартным Bitrix24 REST (`crm.deal.list` и
т. п.) — это было явно помечено как допущение. После сверки с
`docs/entity-api`, `docs/infra` и `docs/infra/app-runtime` оказалось:

| Было (догадка)                          | Стало (подтверждено документацией)                                  |
| ---------------------------------------- | --------------------------------------------------------------------- |
| Базовый URL `api.vibecode.bitrix24.tech` | `https://vibecode.bitrix24.tech`                                     |
| `crm.deal.list`, `crm.status.list`       | `POST /v1/deals/search`, `GET /v1/statuses?filter[entityId]=…`       |
| Поле `OPPORTUNITY`                       | `amount`                                                               |
| Токен как единственный заголовок         | `X-Api-Key: <ключ приложения>` **+** `Authorization: Bearer <сессия>` |
| Ручная пагинация через `/v1/batch`       | Один вызов `search` с `limit` до 5000 — платформа пагинирует сама    |

## Архитектура

- **BFF-паттерн**: фронтенд (`public/`) ходит только к `/api/me` и
  `/api/dashboard`. Всё обращение к V1 API — в `VibeClient.php`.
- `auth.php` доверяет только заголовку `X-Vibe-Authorization`, который
  на каждый запрос кладёт Gateway (подделать его снаружи нельзя —
  Gateway срезает любой входящий `X-Vibe-Authorization` от клиента).
- **Важный нюанс реального API**: платформа не даёт серверу
  автоматический доступ к `/v1/{entity}` только по сессии пользователя.
  Нужен ещё **собственный ключ приложения** (`VIBE_APP_KEY`, `vibe_app_…`)
  в заголовке `X-Api-Key` — он выпускается один раз в разделе «Ключи
  авторизации» и передаётся приложению через `env` при деплое. Сессия
  пользователя (`Authorization: Bearer`) обеспечивает per-user права
  доступа к данным, `X-Api-Key` определяет, какое это приложение.
  Подробности — `docs/infra/app-runtime`, раздел «Приложение как
  сервис: собственный ключ (X-Api-Key)».

## Переменные окружения

См. `.env.example`. **`VIBE_APP_KEY` обязателен** — без него любой вызов
к `/v1/{entity}` вернёт ошибку `MISSING_APP_KEY` (наша собственная
проверка, до похода в сеть). Сам `.env` не коммитить.

## Деплой через Deploy API (без SSH)

Ваш сервер в режиме Black Hole — прямого SSH нет, деплой идёт через
`POST /v1/infra/servers/:id/deploy`, как показано в разделе «Деплой» на
экране приложения. Порядок:

### 1. Создать ключ приложения (если ещё не создан)

В разделе «Ключи авторизации» на портале Вайбкод создайте ключ типа
**авторизации (`vibe_app_`)** — приложение встраивается в портал и
многопользовательское. Запрошенные скоупы: `crm` (сделки, стадии),
`users` (имена ответственных). Если платформа позволяет — включите
режим `READONLY`: приложение только читает данные.

### 2. Собрать архив кода

```bash
cd deal-funnel-dashboard-php-v2
tar -czf app.tar.gz --exclude='.env' --exclude='.git' .
```

### 3. Задеплоить через Deploy API

Ваш endpoint с экрана «Деплой»:
`POST /v1/infra/servers/22ee2bfa-fad4-4491-9dc7-97c5ea37a8aa/exec` —
это для одиночных команд. Для полной выкладки кода используйте
`/deploy` на том же сервере (тот же `id`, другой путь):

```bash
export VIBE_KEY="<ваш ключ платформы для инфра-операций>"
export SERVER_ID="22ee2bfa-fad4-4491-9dc7-97c5ea37a8aa"

B64=$(base64 < app.tar.gz | tr -d '\n')

curl -X POST "https://vibecode.bitrix24.tech/v1/infra/servers/$SERVER_ID/deploy" \
  -H "X-Api-Key: $VIBE_KEY" \
  -H "Content-Type: application/json" \
  -d "{
    \"source\": { \"content\": \"$B64\" },
    \"runtime\": \"php83\",
    \"start\": \"php -S 0.0.0.0:3000 -t public router.php\",
    \"port\": 3000,
    \"env\": { \"VIBE_APP_KEY\": \"<ключ приложения из шага 1>\" },
    \"displayName\": \"Дашборд продаж\",
    \"description\": \"Сводка по воронке, KPI и последние сделки CRM\"
  }"
```

Если архив крупнее ~72 МБ (маловероятно для этого проекта — код весит
считаные килобайты), используйте `"source": {"url": "..."}` со ссылкой
на архив вместо `content`, с заголовком
`X-Skip-Source-Snapshot: deploy from external URL`.

**Таймаут клиента:** ставьте `--max-time 690` (curl) или ≥ 690 секунд —
платформа удерживает соединение до 660 секунд на самом деплое, плюс до
6.5 минут, если сервер спал. Короткий таймаут клиента не отменяет
деплой на сервере — он просто не увидит финальный ответ.

**Проверяйте `success` в теле ответа, а не HTTP-статус** — при деплое
на отдельной виртуальной машине статус `200` приходит и на успех, и на
провал; признак провала — `"success": false` и `error.step`.

### 4. Встраивание в портал

Приложение должно быть привязано как placement (левое меню / вкладка
CRM) через обработчик платформы `https://vibecode.bitrix24.tech/v1/bitrix-handler`
— это делается один раз при регистрации приложения на портале, а не
командой из этого README. Если placement уже привязан напрямую к
субдомену — перепривяжите через `POST /v1/apps/:id/placements`
(см. `docs/apps/placements/bind`): иначе Gateway не создаст сессию, и
вместо приложения будет показан экран входа.

### 5. Проверка после деплоя

```bash
curl -H "X-Api-Key: $VIBE_KEY" \
  "https://vibecode.bitrix24.tech/v1/infra/servers/$SERVER_ID"
# Ждите status=running И blackholeStatus=CONNECTED
```

Откройте приложение из портала и сверьте `GET /api/me` (наш прокси к
`GET /v1/me`) — там будут фактические скоупы, тип ключа и `portal`.

## Локальная проверка синтаксиса

```bash
php -l VibeClient.php
php -l api/dashboard.php
php -l api/me.php
```

Полноценно поднять `/api/*` локально без Gateway нельзя — эндпоинты
требуют заголовок `X-Vibe-Authorization`. Для точечной проверки
подставляйте тестовый токен вручную (потребуется реальный `VIBE_APP_KEY`
в `.env`):

```bash
php -S 0.0.0.0:3000 -t public router.php &
curl -H "X-Vibe-Authorization: Bearer <тестовая_сессия>" \
     "http://localhost:3000/api/dashboard?dateFrom=2026-06-01&dateTo=2026-09-01"
```

## ⚠️ Единственное оставшееся допущение

Названия полей в ответе `GET /v1/statuses` (справочник стадий) и
`GET /v1/users` (имена сотрудников) взяты по установленной платформой
конвенции camelCase (`id`/`name`, `name`/`lastName`) — это подтверждено
для полей сделки (`docs/entities/deals/fields`) и явно описано как общее
правило для всех сущностей в `docs/entity-api`, но отдельная страница
`docs/entities/statuses/fields` / `docs/entities/users/fields` не
проверялась напрямую. Если названия окажутся другими — правка в двух
местах `api/dashboard.php` (`fetchStageLabels`, `fetchUserNames`), вся
остальная логика не пострадает.
